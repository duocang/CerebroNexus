# Deploy the checkout being reviewed

Build the runtime from the same revision used to generate the app. This avoids
silently installing the default GitHub branch into a PR test deployment.

```sh
git rev-parse HEAD
docker build -f deploy/Dockerfile -t cerebronexus-viewer:review .
docker build -f deploy/App.Dockerfile \
  --build-arg VIEWER_IMAGE=cerebronexus-viewer:review \
  -t cerebronexus-app:review /absolute/path/to/deployment
docker run --rm --name cerebro-review \
  -p 127.0.0.1:3838:3838 \
  --env-file /absolute/private/viewer-auth.env \
  cerebronexus-app:review
```

The deployment directory contains `my_app/`, generated by `createShinyApp()`.
Keep the env file outside both build contexts. Omit `--env-file` for an app
without authentication. In WSL, generate authenticated apps under `/home`,
where private Unix file modes work, rather than under `/mnt/c`.

`deploy/Dockerfile` defaults to `mihem/shinyapps_3838:v9.0`, installs missing
runtime dependencies, validates them in a fresh R process, then installs the
local source. Use `--build-arg BASE_IMAGE=...` to test another compatible base.
Dependency downloads are not a lockfile: record the resulting image ID/digest
alongside the Git revision when handing a build to another reviewer.

`deploy/App.Dockerfile` sets ownership to the `shiny` runtime user and enforces
private authentication database modes. It does not require changing ownership
of a live service or making the database world-readable.

Open <http://localhost:3838>. Check invalid and valid login, Projection,
Spatial/dataset switching, and the browser console. Inspect `docker logs
cerebro-review` for server errors. A successful image build alone is not an
end-to-end deployment acceptance test.
