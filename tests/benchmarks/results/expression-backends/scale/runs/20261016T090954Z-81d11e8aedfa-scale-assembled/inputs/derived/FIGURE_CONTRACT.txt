Question: how do interactive latency, block latency, loaded memory and storage change from common subsets to the full datasets?
Claim boundary: observed backend trade-offs on these two datasets and this machine, not universal complexity or a fixed-gene scaling experiment.
Archetype: quantitative grid, four metric rows and two dataset columns.
Evidence roles: warmed single-gene latency (interaction), 12-gene block latency (multi-gene workload), loaded RSS (memory feasibility), total storage (disk cost).
Backend: R ggplot2/patchwork, adapted structurally from the repository's scale plot; existing raw results and plotting source remain intact.
Mapping: source -> dataset; n_cells -> actual x position; backend -> colour/shape; hot_p50_secs/block_secs -> seconds; rss_mb/total_mb -> GiB after /1024.
Statistics: each metric uses all successful observations. Access metrics first take the median of the two processes belonging to each build, then median and min-max across five builds. Storage uses five builds directly. These ranges are descriptive, not confidence intervals.
Exception: Human embedded 500k is one build with two nested reads, drawn as a disconnected hollow diamond with no between-build error bar. It does not establish five-build repeatability.
Exclusions: five resource-skipped Human PFC embedded builds at 500k have no values. Embedded 1m/full was not scheduled. No invented values or interpolated measurements.
Comparability: profiles panel_c2 and scale share 12 query genes, three hot repetitions, five builds, two independent access processes, materialized-v2 and monotonic-v1. Genes are selected per tier; joined points do not isolate the effect of cell count alone.
